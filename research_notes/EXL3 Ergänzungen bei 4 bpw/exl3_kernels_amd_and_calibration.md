## A1. How EXL3 inference works (format, procedural codebooks, 16x16 tiles, had_r_128, GEMV vs reconstruct paths, reported throughput)

### Takeaway
EXL3 stores weights as 16x16 bitshift-trellis tiles (8·bits uint32 words per tile), with a 128-point Hadamard plus ±1 sign/scale vectors (`suh` on the input side, `svh` on the output side) applied in 128-wide independent blocks. Decode of the default `mul1` codebook costs roughly one 32-bit IMUL, one dp4a byte-sum, one int-to-half convert and one HFMA per weight plus an amortised funnel-shift; the small-M path (≤144 rows) runs a fused cooperative GEMV/GEMM with MMA on the decoded fragments, while ≥144 rows reconstructs fp16 weights and calls a plain hgemm (fused "original basis" reconstruct for ≥1024 rows). Turboderp publishes no fp16/GPTQ-relative kernel numbers; code comments show the M=1 GEMM on a 3090 is not purely bandwidth-bound (fp16 accumulation alone gains ~14%, register pressure costs 18–28%).

### Cited Findings
- EXL3 is "a streamlined variant of QTIP from Cornell RelaxML"; Hessians are computed on the fly during conversion using "a fused Viterbi kernel" (author, README) — [exllamav3 README](https://github.com/turboderp-org/exllamav3)
- Tensor layout (author, `exl3.py`): `trellis` is a 3-D int16 tensor; tiles are 16 columns wide; bitrate K = `trellis.shape[-1] / 16`; code comment: "Bitrate from the tile width: 16 * K uint16 per tile, 16 * K + 8 for half-integer K (mul1 only)". `suh`/`svh` are fp16 vectors used at runtime; packed `su`/`sv` bitfields are "Only used for full reconstruct and loading old models, not during inference". There is no per-tensor scalar scale ("scale is no longer used"). — [exl3.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/modules/quant/exl3.py)
- Forward-path selection (author, `exl3.py`): direct fused kernel (`bc.run_alloc`) when `rows <= AUTO_RECONSTRUCT_THRESHOLD` (= 144); otherwise `reconstruct_hgemm`. Inside it, the fused reconstruct (`ext.reconstruct_had_slice`, emits original-basis weights so no input/output Hadamard launches) is used only when `rows >= 1024` and `in_features % 128 == 0 and out_features % 128 == 0`; comment: "The fused kernel costs ~4x plain reconstruct (k*n-proportional) while the saved had launches scale with rows*(k+n); breakeven is rows ~400-900 across shapes". The unfused path does `had_r_128(x, xh, suh)` → `ext.reconstruct`/`reconstruct_slice` → `ext.hgemm_recon(xh, w, y)` → `had_r_128(y, y, None, svh)`. Output slices are capped at `MAX_RECONSTRUCT_SLICE_N` = 32768 columns. — [exl3.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/modules/quant/exl3.py)
- `reconstruct_columns` docstring: "A column leaves the trellis only together with its 128-wide output Hadamard block"; comment on fused path: "Requires 128-divisible dims (always true for EXL3 tensors: both sides are had-transformed at quant time)". — [exl3.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/modules/quant/exl3.py)
- Hadamard kernel (author, `hadamard.cu`): `had_r_128` computes `y = (x.view(-1, 128) @ had_128).view(x.shape)`; output may alias input; `r_scale = scale * 0.088388347648f` ("scale / sqrt(128)"); one warp (32 threads, `__launch_bounds__(32)`) per 128-element chunk; grid = (rows, cols/128); each chunk is transformed independently; `pre_scale` (suh) and `post_scale` (svh) are fp16 vectors selected via kernel templates. — [hadamard.cu](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/hadamard.cu)
- Tile dequant (author, `exl3_dq.cuh`): a 16x16 tile = 256 weights occupies `8 * bits` uint32 words; each weight's 16-bit state is a sliding window advancing by `bits` bits (windows overlap by 16−bits bits); generic path = two 32-bit loads + `__funnelshift_r` + mask per weight; `dq8` aligned variants cut funnel-shifts per 8 weights from 8 → 4/2/1 (align 2/4/8), and `dq8_aligned_4bits_bfe64` uses eight `bfe64` extracts from a 64-bit view; half-integer rates alternate KA and KA+1 bits ("bits2 = 2*KA + 1" per pair); `dq_dispatch`: 1/2/4 bits → aligned kernels, 3 bits → `dq8<3,cb,4>`, 5/6/8 → two `dq4`, 7 → two `dq2x2`. Outputs are packed as `half2` pairs into MMA B-fragments. — [exl3_dq.cuh](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/exl3_dq.cuh)
- Codebooks (author, `codebook.cuh`): **mul1** (cb 2): state × `0x83DCD12D`, byte-sum via `__dp4a(x, 0x01010101u, 0x6400u)` (noted "bit-identical" to an earlier `vabsdiff4` form), convert low 16 bits to half, one HFMA with scale `0x1eee` (≈0.00677, "1/147.7") and bias `0xc931` (≈−10.39). **mcg** (cb 1): state × `0xCBAC1FED`, one `lop3.b32` with masks `0x8fff8fff`/`0x3b603b60` (on ROCm a C fallback `exl3_lop3_6a`), reinterpret as two packed fp16 and `__hadd`. **3inst** (cb 0): state × `89226354` + `64248484`, same LOP3, `__hadd`. — [codebook.cuh](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/codebook.cuh)
- Converter doc (author): `-cb/--codebook` = "mul1" (default), "mcg", "3inst"; mul1 "is required by some optimized inference paths (int8 GEMV, CPU expert offload)"; "there's no reason to choose another codebook except for testing". Half-integer rates 1.5/2.5/3.5 exist for mul1 only. — [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md); [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py)
- Small-M GEMV (author, `exl3_gemv_kernel.cuh`): cooperative launch with one `grid.sync` after the input-Hadamard stage and one before the output stage; `MMODE 0` is m==1, `MMODE 1` covers 2 ≤ m ≤ 8 (`EXL3_GEMV_MAX_M`); `CFG 0` ("narrow"): 512 threads, 16 K-split warps, 2 n-tiles/warp, prefetch depth 4 — "wins at attention-projection sizes"; `CFG 1` ("wide"): 256 threads, 8 K-split warps, 4 n-tiles/warp, prefetch 2 — "wins at large-n FFN sizes"; B words are read with `__ldcs` (evict-first) "because B is single-use" through a register prefetch ring; each 16x16 tile gets one `m16n8k16` MMA pair with fp16 accumulators folded into fp32 every FOLD steps; supports 2/3/4 bpw plus 1.5/2.5/3.5 (mul1; "12 / 20 / 28 uint32 per tile"); the register bound (64 regs) matters: without it "ptxas spends 81-85 registers … one 512-thread block per SM instead of two, measured 18-28% slower at attention-projection shapes on the 3090". Input stage applies a 128-point Hadamard per warp with 1/sqrt(128) and `suh`; output stage applies Hadamard with `svh`. — [exl3_gemv_kernel.cuh](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/exl3_gemv_kernel.cuh)
- Large-M GEMM inner (author, `exl3_gemm_inner.cuh`): 256 threads (8 warps); `TILESIZE_M` multiple of 16 ("16 for decode, 32 or 64 for fused-MoE prefill"), `TILESIZE_K` multiple of 16, `TILESIZE_N` multiple of 128; A staged in shared memory with 16-byte `cp.async`, XOR-swizzled, `SH_STAGES` pipeline, read with `ldmatrix` (`ldsm4`); B tiles (`TILE_U16 = 16*bits (+8 if half_k)` uint16) staged raw in smem and decoded per warp via `dq_dispatch`; `FRAG_STAGES` (1–5) interleave `load_frags` with `matmul` — "especially important to hide the dequantization overhead"; accumulators fp32, except an sm_86-only fp16-accumulate path: "~14% faster at bsz 1 on RTX 3090", max error "~1% of output RMS at k=4096"; K-split across blocks via per-column locks (no atomics); output Hadamard applied in 128-column chunks with `post_scale`. — [exl3_gemm_inner.cuh](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/exl3_gemm_inner.cuh)
- `exl3_gemm_kernel.cuh` header: tile inner is "tensor-core MMA with cp.async pipelines (CUDA) or WMMA on RDNA (rocm/quant)"; on ROCm the grid sync is a device-counter `group_barrier` and "every block is resident"; the `mgemm` (multi-matrix) variant uses `group_barrier` on ROCm and SM > 890. — [exl3_gemm_kernel.cuh](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/exl3_gemm_kernel.cuh)
- Kernel-selection env vars (author, `doc/env_vars.md`): `EXL3_GEMV` (1 = heuristic; "QTIP-style small-m fp16 GEMV"), `EXL3_GEMV_SMEM` (−1 per bitrate: shuffles vs shared-memory extraction), `EXL3_INT8_GEMV` (default 2 on CUDA, **0 on ROCm**; "Fused int8-activation GEMV for mul1 tensors"), `EXL3_INT8_GEMV_MAX_K` (6 on Hopper/Blackwell else 5), `EXL3_HGEMM_F16ACC` (fp16-accumulator MMA for reconstruct GEMMs on GeForce; 0 = cuBLAS), `EXL3_NO_FUSED_RECONSTRUCT`, `EXL3_MGEMM_K/N_THRESHOLD` (N 8192). — [doc/env_vars.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/env_vars.md)
- QTIP reference kernels (author, Cornell): bs=1 on RTX 6000 Ada with q/k/v and up/gate fusion: FP16 55.9 tok/s (2-7B), AQLM 2-bit 81.5, QuIP# 2-bit 186, QTIP 2-bit 188; 2-70B: QTIP 23.5, QuIP# 22.2 (FP16 OOM). Kernel parameters L=16, Q=9, V=2, Tx=Ty=16; codes HYB (`quantlut_sym`), 3INST, 1MAD, pure LUT; "public models should get 80-90% of matrix fusion speeds". — [Cornell-RelaxML/qtip](https://github.com/Cornell-RelaxML/qtip)
- QTIP paper (search snippet; paper itself unreachable): the bitshift trellis means "obtaining the next compressed group of V weights … only requires bitshifting by kV bits"; compute-based codes give "a pseudorandom approximate Gaussian from an L-bit input in 4 or fewer GPU instructions"; 1MAD = LCG then sum of four 8-bit values; 3INST = float bit-tricks; 2-bit i.i.d. Gaussian MSE 0.069 (1MAD and 3INST) vs 0.068 (RPTC lookup). — [arXiv 2406.11235](https://arxiv.org/abs/2406.11235v4)

### Inferences
- Per-weight decode cost for mul1 on NVIDIA ≈ IMUL + DP4A + CVT + HFMA + ~0.125–1 funnel-shift (amortised) + the share of an m16n8k16 MMA; for mcg/3inst the LOP3 collapses to one instruction on CUDA but becomes a multi-op C fallback on ROCm (`exl3_lop3_6a`), so on AMD mul1 is the cheaper codebook as well as the only one with the fast paths (int8 GEMV, `v_sad_u8` byte-sum trick in the RDNA kernels, see A2).
- The 3090 comments (fp16-accumulate +14% at bsz 1; register pressure −18–28%) and the ik_llama 4080 data (trellis 2-bit ≈25% slower than IQ2_XXS at ~same bytes) both indicate the trellis decode is only *partly* hidden under memory bandwidth at M=1 on NVIDIA consumer parts; on RDNA with wave32, no dp4a-equivalent packed byte-sum except `v_sad_u8`/`v_dot4`, and no `lop3`, expect the compute share to be larger, which is exactly what the fork's "WMMA was slower than dual-issued v_dot2" finding suggests.
- For a "GEMM time on one layer" benchmark: at M=1 the EXL3 path is the cooperative GEMV (register prefetch, evict-first loads) and should be judged against bytes moved (4 bpw ≈ 0.5 B/weight + 2×2 B per 128-vector for suh/svh, i.e. ~0.1% overhead) rather than fp16; at M in the thousands the relevant cost is the one-time reconstruct (k·n fp16 write, "~4x plain reconstruct" for the fused variant) plus an ordinary hgemm, so dequant overhead at prefill is amortised to near zero and the comparison with int4/MXFP4 kernels will be dominated by the hgemm's own efficiency on the target GPU.

### Gaps
- No turboderp-published table of EXL3 GEMV/GEMM throughput relative to fp16, GPTQ or AWQ kernels was found (the repo's `science/qgemm_benchmark.py` exists but its outputs are not published in text form).
- `hadamard_inner.cuh`, `exl3_kernel_map.cuh` (actual TILESIZE values per bitrate) and the `comp_units/` folder were not read; concrete smem bytes per config are therefore not reported.

## A2. ROCm / AMD / RDNA4 status of exllamav3 and existing HIP ports of trellis decoders

### Takeaway
As of October 2026 exllamav3 has official but "preliminary" ROCm support (release 1.6.0, 7 Oct 2026: "ROCm 10 only, gfx1100+"), with a dedicated `exllamav3_ext/rocm/quant` tree containing RDNA GEMV/GEMM/MoE variants (WMMA-based), and it has been run on gfx1201 (R9700 and RX 9070 XT) by several users — including a full model conversion on an R9700 within 0.4% PPL of bf16 — but the ROCm kernels are still clearly behind the CUDA ones and several RDNA4-specific bugs/perf issues are open. An independent MIT-licensed RDNA3 port (`phoenixhaxor/exllamav3-rocm`, gfx1100 only) exists with wave32 `v_sad_u8`/`v_dot2` trellis kernels that turboderp is porting upstream (PR #547 etc.). No HIP port of the original QTIP kernels and no trellis decoder in mainline llama.cpp/vLLM/SGLang/MLX was found; ik_llama.cpp's KT trellis quants run on CUDA/Metal/CPU and its ROCm backend is "not actively maintained".

## A3. Dequant overhead of other formats (int4 g128, Q4_0/Q4_K/Q5_K on RDNA3/RDNA4, MXFP4, trellis KT quants) for estimating an EXL3 GEMM timing

### Takeaway
Public RDNA4 kernel data is almost entirely llama.cpp `llama-bench` numbers: on an R9700, Llama-2-7B Q4_0 reaches ~94–98 tok/s tg128 and ~4.4–4.8k tok/s pp512, and a 27B Q5_K_M dense model ~24.9 tok/s tg128 / ~956 tok/s pp512 (implying roughly 370–470 GB/s effective weight bandwidth at M=1). Marlin-style int4 kernels reach ~3.87x over fp16 at M≤32 on NVIDIA; ik_llama's QTIP-style IQ2_KT runs ~25% slower than IQ2_XXS at the same size on an RTX 4080, giving a concrete upper bound on what a well-written trellis decode costs at M=1 even on NVIDIA. No MXFP4/NVFP4/IQ4_XS-vs-Q4_K_M same-card data for gfx1201 was found.

### Cited Findings
- Marlin (int4, group 128): theoretical max speedup over fp16 is 3.87x (0.125 bit/weight scale overhead); "close to ideal (4x) speedups up to batchsizes of 16-32 tokens" vs 1–2 tokens for prior kernels; GPUs have FLOP/byte ratios "around 100-200", so each 4-bit weight may be used for <25–50 MACs and still be bandwidth-bound; dequant and tensor-core instructions are ordered "so both pipelines stay saturated"; A10 benchmarks, Ampere+ required. — [IST-DASLab/marlin](https://github.com/IST-DASLab/marlin)

R9700 **Qwen3-32B Q4_K_M**: ROCm pp512 498.7, tg128 24.0; Vulkan tg128 28.2. No RDNA card on that page has two quant types on the same model. — [llama.cpp discussion #15021](https://github.com/ggml-org/llama.cpp/discussions/15021)

### Inferences
- Back-of-envelope for the PR #547 shape: 5120×17408 at 4 bpw ≈ 44.6 MB; 81 µs ⇒ ≈550 GB/s effective on a 7900 XTX (spec ≈960 GB/s), i.e. the RDNA3 trellis small-M kernel reaches ~55–60% of peak bandwidth at 5–8 rows — a useful target/sanity bound for a gfx1201 kernel (R9700/9070 XT spec bandwidth ≈640 GB/s, GDDR6 256-bit; AMD spec value, not fetched in this session).
- llama.cpp's Q5_K_M 27B result on the R9700 (≈19 GB of weights at 24.85 tok/s ⇒ ≈470 GB/s ≈ 73% of 640 GB/s) is the practical M=1 bandwidth ceiling a scalar-quant GEMV reaches on this card; an EXL3 4-bpw GEMV that gets ~55% (RDNA3 PR #547 level) would land at roughly 30 tok/s-equivalent for a 27B model, versus ~37 tok/s if it matched the K-quant kernel — so expect a 10–25% decode-kernel penalty for trellis unless the gfx12 WMMA multirow path is tuned.
- At prefill (M in the thousands) EXL3 reconstructs to fp16 and calls hgemm, so its "GEMM time on a layer" is essentially fp16 GEMM time plus a reconstruct that is linear in weight size; scalar int4/MXFP4 kernels that dequantise inside the GEMM (MMQ/Marlin style) avoid the fp16 weight write but on RDNA4 llama.cpp's MMQ vs WMMA-dequant choice is itself still being tuned, so the gap at large M is probably small either way.

### Gaps
- No same-card RDNA4 comparison of Q4_K_M vs IQ4_XS vs MXFP4 vs Q4_0 kernels was found; no NVFP4 numbers on AMD at all; the vLLM native AMD W4A16 kernel article was unreachable.
- No published microsecond-level GEMM timings for EXL3 on gfx1201.

## A4. Tensor-parallel sharding of EXL3 tensors

### Takeaway
EXL3 tensors split cleanly: an output (N) split slices `svh[first:last]` and `trellis[:, first//16:last//16]`, an input (K) split slices `suh[first:last]` and `trellis[first//16:last//16, :]` (bias kept only on rank 0); the codebook constants are replicated. Because `had_r_128` transforms each 128-element chunk independently and the output Hadamard/`svh` is linear, nothing in the format resists K-splitting down/out projections provided cut points are multiples of 128 (the fused reconstruct path requires 128-divisible dims and `reconstruct_columns` works in 128-wide output blocks). exllamav3's own TP works with Qwen3.8-27B and on ROCm (after PR #503), with an all-reduce between layers that turboderp calls "an annoying bottleneck" with "nothing to overlap with".

### Cited Findings
- `tp_import_split` (author, `exl3.py`): output split — `suh` received in full, `svh = svh[first:last]`, `trellis = trellis[:, first//16 : last//16]`, bias sliced; input split — `suh = suh[first:last]`, `svh` in full, `trellis = trellis[first//16 : last//16, :]`, "Bias is kept only when first == 0"; `tp_import_split_n` concatenates several output splits (svh dim 0, trellis dim 1); `mcg`/`mul1` "are received whole in every case, since they are codebook constants". The file "does not assert 128-column alignment for TP splits"; the fused path asserts `% 128 == 0`, and `reconstruct_columns` works in 128-wide blocks. — [exl3.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/modules/quant/exl3.py)
- Hadamard chunks are independent per 128 elements (one warp per chunk, no cross-block communication) — [hadamard.cu](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/exllamav3_ext/quant/hadamard.cu)
- TP all-reduce (turboderp, 25 Oct 2026): "Each layer starts with the output from the previous layer, and the all-reduce sits in between"; "nothing to overlap with"; "an annoying bottleneck"; backend is a CPU shared-memory all-reduce or NCCL; Qwen3.8-27B 4.0 bpw ran TP on 2× T4 without P2P at 18–19 tok/s (55–57 with DFlash2). — [issue #568](https://github.com/turboderp-org/exllamav3/issues/568)
- TP env vars: `EXLLAMA_NO_P2P_COPY`, `EXLLAMA_MASTER_ADDR/PORT` (rendezvous), `EXL3_TP_NO_FP16_WIRE`, `EXL3_TP_NCCL_FP32`, `EXL3_TP_REDUCE_MAX_ISA` (avx/avx2/avx512 CPU reduce), `EXL3_TP_REDUCE_THREADS`, `EXL3_TP_NO_FWD_BARRIER`. — [doc/env_vars.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/env_vars.md)
- Release notes: 1.5.1 "TP support for Qwen3.8-Flash-Next, GLM5.3, and DeepseekV3/V4"; 1.5.3 "dynamic draft sizing with TP models"; 1.6.2 "TP support for models with DFlash2 drafters"; 1.6.4 "TP and shared-memory fixes". — [releases](https://github.com/turboderp-org/exllamav3/releases)
- PR #503 (merged 11 Oct 2026) fixed TP on ROCm without PCIe atomics (gfx1100; kernels with device-side printf failed to launch, loader thread hang, 50 s helper idle deadline). — [PR #503](https://github.com/turboderp-org/exllamav3/pull/503)
- An older README mirror stated Qwen3-Next support was "experimental … does not support tensor/expert parallelism" (date unknown, superseded by 1.5.1 notes) — [search result](https://scriptagc.wasmer.app/https_github_com/turboderp-org/exllamav3)
- Qwen3.8-27B shapes seen in kernel benchmarks: k=5120, n=17408 (PR #547) — [PR #547](https://github.com/turboderp-org/exllamav3/pull/547); the model is `qwen3_5` arch with 64 layers of which 16 carry KV cache (issue #544). — [issue #544](https://github.com/turboderp-org/exllamav3/issues/544)

### Inferences
- For TP=2 on Qwen3.8-27B: hidden 5120 = 40×128 and intermediate 17408 = 136×128, so halves (2560 = 20×128, 8704 = 68×128) stay 128-aligned; a K-split of `down_proj` gives each rank 68 Hadamard blocks of its own input, applies its `suh` slice + per-block Hadamard locally, runs the trellis GEMV on its 544-tile-row slice, applies the (linear) output Hadamard + full `svh`, and the all-reduce of partial outputs is exact. Row-splitting at a non-multiple of 128 would break a Hadamard block across ranks and is the only real constraint.
- For a custom "radiance" plugin the same slicing applies to the packed tile array: a K-slice is a contiguous range of tile rows (16 weights each), so no re-packing is needed.

### Gaps
- The TP splitter that calls `tp_import_split` (which decides split points) was not read; whether it enforces 128-multiples explicitly is inferred, not confirmed.
- No TP=2 scaling numbers for EXL3 on two R9700s (or any two AMD cards) were found.

## B1. Self-calibration ("SC_") pipeline: sc_trace / sc_rfn_probe / sc_measure / sc_optimize, reported gains, SC_4.00bpw_H5 vs 4.00bpw

### Takeaway
"Self-calibration" means (1) generating ~512K tokens of the model's own chat-template outputs over ~157 seeded multi-domain, 20-language prompts (`sc_trace.py`, 250×2048 rows), (2) measuring per-tensor end-to-end KLD sensitivity by injecting (Hessian-shaped) noise (`sc_measure.py`, ~35 min for a 27B), (3) solving a greedy per-tensor bit allocation under the cost model `kld = S_t · rfn_t(K)^α` with rfn halving ~1.96x per bit (`sc_optimize.py`), and (4) converting with that recipe and the trace as calibration data. Turboderp reports only internal validation (Spearman 0.84 shaped vs 0.61 unshaped against swap attribution; whole 27B pipeline ≈2 h) and no end-to-end KLD gain; a third-party WikiText-2 KLD sweep found turboderp's SC_4.00bpw_H5 (0.0214) *worse* than the plain 4.00bpw (0.0159) on wikitext, consistent with the doc's own warning that recipes are domain-specific.

### Cited Findings
- Pipeline (author, doc/optimize.md): trace (`sc_trace.py`: ~140 seeded conversations, 19 languages, default 250×2048 packed rows) → optional `sc_rfn_probe.py` (per-tensor rfn = ‖W_q−W‖/‖W‖ from an existing conversion; otherwise global `--anchor 2:0.292`) → `sc_measure.py` (seeded noise into one tensor of the unquantized model, suffix forward pass, KLD of final logits; `--shaped` uses per-layer Hessians and LDLQ-style error) → `sc_optimize.py` (greedy allocation, "optimal since the curves are convex", plus exchange-repair; `--tie` defaults share bitrates for fused GEMMs) → `convert.py -rcp … -cd …` → `eval/qbench.py` on a disjoint held-out trace (`--tool_frac` 0.3). Rationale: on the model's own output "the usual U-shape largely flattens" and "small mid-stack attention projections (k/v)" become the most valuable bits. Status: "experimental", "currently untested on sparse models". — [doc/optimize.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/optimize.md)
- Validation and runtime (author, optimize.md): shaped-noise predictions reach Spearman 0.84 vs ground-truth swap attribution (0.61 unshaped); isotropic noise overestimates sensitivity "by up to ~6x" (v_proj worst); full run for a ~27B dense model "roughly two hours on a single fast GPU, mostly spent on conversion"; sensitivity measurement ≈35 min with two noise levels, resumable; needs the unquantized model plus Hessians — "A 27B model in bf16 fits in 96 GB"; "Wikitext-measured recipes transfer poorly"; fitted α "runs low (~1.7–1.9)", recommends `--alpha 2.0`; measured K2→K1 demotion exponent ≈2.35 on Qwen3.8-27B; the eval trace must be disjoint "or the gains are overstated"; optimizer prints predicted KLD vs an ends-first baseline but **no measured end-to-end gains are given in the doc**. — [doc/optimize.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/optimize.md)
- `sc_measure.py` (author): iid noise "overestimates KL against real swap attribution on qwen3.8-27b (median 1.95x, up to 5.8x on v_proj)"; defaults `--rows 10`, `--length 1024`, `--draws 1`, `--h_rows 64`, `--rfn 0.29,0.145`, `--rfn_scale 1.0,0.5`; grouped targets (q/k/v, gate/up, GDN qkv/z, MoE experts) measured as one unit; streaming load mode for models that don't fit; asserts an fp16 (unquantized) model; "Not validated on MoE models". — [sc_measure.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/sc_measure.py)
- `sc_optimize.py` (author): `rfn(K) = anchor_rfn · bit_ratio^(anchor_K − K)` with `--bit_ratio 1.96` and `--anchor 2:0.292` (⇒ rfn ≈ 0.149 at K3, 0.076 at K4, 0.039 at K5, 0.020 at K6 — arithmetic, not in source); greedy from `--min_k` by `--k_step` (0.5 allowed for mul1 half rates), up to 100 exchange-repair passes; actual default `--tie` is `q_proj+k_proj+v_proj,gate_proj+up_proj,in_proj_qkv+in_proj_z` (help text outdated); baseline "floors the target bitrate everywhere, then promotes tensors to the next integer starting from the stack ends"; output YAML has `target_bpw`, `achieved_bpw`, `predicted_kld`, `head_bits`, `tie`, `tensors:` map. — [sc_optimize.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/sc_optimize.py)
- `sc_trace.py` (author): ~157 seed prompts across reasoning, math, coding, science, medicine, history, economics, philosophy, creative/professional writing, structured output, summarisation, roleplay, cooking, sports, DIY, tech, translation, mixed formats; English + 19 languages; rows are full templated conversations from position 0, right-padded, with a `lengths` tensor; default 250×2048 = 512,000 tokens; `--max_new_tokens 3072`, up to 4 epochs; source should be "the unquantized model or a high-bitrate quant (e.g., 6 bpw)". — [sc_trace.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/sc_trace.py)

- "SC_4.00bpw_H5" = self-calibrated recipe + trace calibration at 4.00 bpw mean with `head_bits` 5 ("H5"); "V6" in derived names most likely denotes an embedding/vision or recipe version, not confirmed. The 3.73x/bit user figure matches the optimizer's rfn ratio 1.96/bit under α≈2 (1.96² ≈ 3.84).
- The wikitext KLD penalty of SC quants (~+35% at 4 bpw) is the expected flip side of optimising for the model's own chat distribution; for the user's challenge, whose scoring uses "golden distributions" on in-domain data, the right move is to run `sc_measure` with `--shaped --trace <in-domain rows>` (or rows built from the challenge's domain) rather than the stock trace, and to evaluate on a disjoint in-domain set.
- The optimizer's rfn curve is only an anchor; using `sc_rfn_probe.py` on a quick plain conversion of Qwen3.8-27B gives per-tensor anchors and removes the global-anchor assumption, which matters for the GDN in_proj tensors whose error curves may differ from attention/MLP.

## B2. `--hessians` (precomputed hin/hout, YAQA-style) and `--out_scales yaqa`: what they skip and what was reported

### Takeaway
`--hessians DIR` loads one `<tensor_key>.safetensors` per tensor with fp32 `hin` (in×in), `hout` (out×out) and/or `hout_diag`, each symmetric matrix stored as a packed row-major upper triangle (or full square); tensors with `hin` skip the calibration forward passes entirely, tensors with `hout` switch to two-sided LDLQ (unless `-h1`), and `--out_scales yaqa` uses `hout_diag` to weight output channels. The challenge's Σxxᵀ files are exactly the `hin` format. Turboderp's own note: on Qwen3.5-2B the *online* quantised-stream `Hin` combined with a precomputed `Hout` beat the fully precomputed (iterated) pair, and at 250 rows the quantized model "didn't seem to care" which `Hout` variant was used; YAQA support is labelled "highly experimental" (1.5.1).

### Cited Findings
- Converter help (author): `-hess/--hessians`: "Directory of precomputed per-tensor Hessians (<key>.safetensors with hin (in, in) and/or hout (out, out) square or packed upper triangle, and/or hout_diag, e.g. YAQA-style Kronecker factors from a separate gradient pass. Tensors with hin skip the calibration forward passes; tensors with hout use two-sided LDLQ"; `-h1/--hessians_one_sided`: "keep the regular one-sided LDLQ for tensors that have hout, leaving the output side to --out_scales yaqa"; `-hreg/--hessians_reg`: "Diagonal regularization of the output-side Hessian, relative to its mean diagonal (default: same as input side, 0.025). Larger values blend toward plain one-sided LDLQ"; `-sh/--scaled_hessian` (experimental): fold input channel scales into the Hessian "so LDLQ's error feedback weights each row by what its error costs at the output"; code: `hin` is loaded only when no calibration state exists for that tensor; missing file → "No precomputed Hessian for {key}, quantizing uncalibrated"; "Batched group quantization has no two-sided LDLQ: per-tensor path when precomputed Hessians are in play". — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py)
- `--out_scales`: "always, never, auto (default): always, except for gate and up projections of gated MLPs whose calibration statistics predict a lower error without, or yaqa: per-channel scales that account for how much each output channel matters from the diagonal of the output-side Hessians in --hessians (tensors without one are treated as in auto)"; an export made with `--diag` "holds only the diagonal, which affects output scales but not rounding". — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py); [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md)
- `util/yaqa_hessians.py` (author): Kronecker-factored Hessians after YAQA (Tseng, Sun, De Sa 2025) estimated as Fisher information with targets sampled from the model's own distribution; per token `(d_t d_tᵀ) ⊗ (x_t x_tᵀ)`; power iteration: forward pass `Hin = Σ x_t x_tᵀ` ("the usual GPTQ/LDLQ Hessian"), `Hout = Σ (x_tᵀ Hin x_t) d_t d_tᵀ / ‖Hin‖_F²`, alternating; `-s out` (default) = only Hout from one forward + one backward pass — "on Qwen3.5-2B, the online (quantized-stream) Hin from a regular conversion combined with this Hout beat the fully iterated pair"; `-s both` (default 6 passes) ⇒ "Conversion then needs no calibration data"; `--unweighted`, `--diag` options; **format: one file per tensor, keys `hin`, `hout`, `hout_diag`, fp32, symmetric matrices "stored as a packed row-major upper triangle (1-D, n(n+1)/2 values)", full square also accepted**; the output head gets `hin` only ("its hout would be vocab × vocab"); only `nn.Linear` modules (no fused MoE experts); memory `in² + out²` fp32 per tensor, `-l/--layers` ranges, `-rv/--reserve_vram`, `--tf32` ≈40% faster on a 2B and 20% on a 27B; sampling noise: two seeds differ ≈20% (Frobenius) at 250 rows, ≈40% at 64 rows (~1/√rows); "At 250 rows, the quantized model reportedly didn't seem to care about the variant"; skips names `visual`, `vision`, `mtp`, `audio` and "small projections that EXL3 leaves unquantized". — [util/yaqa_hessians.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/util/yaqa_hessians.py)
- Release 1.5.1: YAQA support "highly experimental". — [releases](https://github.com/turboderp-org/exllamav3/releases)
- An open conversion PR (#529, 18–27 Oct 2026) adds "affinity-weighted expert Hessians and a capture-only path for block-sparse layers" (MoE only). — [issues list](https://github.com/turboderp-org/exllamav3/issues?q=Qwen3.8+OR+GDN+OR+DeltaNet+OR+Qwen3-Next+OR+Qwen3.5)
- Default calibration (author): 250 rows × 2048 columns from a bundled corpus mix, replaced by `-cd` packed rows; calibration rows that go non-finite are excluded and the job aborts if >10% are bad (`check_bad_rows`). — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py)

### Inferences
- The challenge Hessians (Σxxᵀ over 10M in-domain tokens, packed upper triangle) can be written directly as `hin` into per-tensor safetensors (keys must match the HF checkpoint tensor names, e.g. `model.layers.N.mlp.down_proj.weight`-style keys as used by exllamav3) and passed with `-hess`; this skips the ~calibration forward passes and makes conversion much cheaper, but it trades away the converter's error-propagating quantised-stream Hessian (later layers see the quantised outputs of earlier layers). Turboderp's 2B observation that online-Hin + precomputed-Hout beat fully precomputed factors is a hint that the online stream is worth something; a direct A/B on Qwen3.8-27B is not available.
- Since the regulariser `-hreg` default equals the input-side 0.025 relative-diagonal damping, a 10M-token `hin` (vs 512K tokens online) should be better conditioned; 20x more tokens also reduces the ~1/√rows noise that turboderp measured for `hout`.
- Without `hout`/`hout_diag` the converter stays one-sided and `--out_scales` behaves as `auto`; computing a cheap `--diag` export (one forward+backward, in-domain) would unlock `--out_scales yaqa` at little cost and is the lowest-risk YAQA option given "highly experimental" status of the two-sided path.

### Gaps
- No published numbers (from turboderp or users) comparing conversions with precomputed `hin` vs online calibration on any model; the only qualitative note is the Qwen3.5-2B remark in the script docstring.
- `science/yaqa.md` referenced by convert.md does not exist on master or dev (404).

## B3. Known pitfalls: calibration length vs long context, data mismatch, ends-first promotion, head/embed bits, resume, VRAM, run time

### Takeaway
Defaults: 250×2048 calibration rows, `head_bits` 6, `embed_bits` 16 (unquantized), `mtp_bits` 4, mul1 codebook; the budgeted allocation floors every tensor at the largest supported rate ≤ target and promotes whole groups one step at a time ordered by module `q_priority`, then by distance to the nearer end of the stack ("End layers contribute disproportionately to end-to-end error"); `-hq` raises per-module floors after the budget is spent and can push the average above `--bits`. Conversion is resumable (`-r`) but `bits`, `recipe`, `head_bits`, `hq`, `cal_*` and `hessians` cannot be changed on resume; VRAM headroom is max(1.5 GB, 6%), the whole SC pipeline for a 27B is ~2 h on "a single fast GPU", `sc_measure` wants the bf16 model resident (96 GB) or streaming mode, and on ROCm/glibc converter RSS can grow ~3.7 GB/layer.

### Cited Findings
- Allocation (author, `allocation.py`): budgeted tensors start at `rate_floor(bpw)`; `max_bits = int(bpw * sum_numel)`; groups ordered by (1) highest module `q_priority`, (2) "Distance to the nearer end of the layer stack … End layers contribute disproportionately to end-to-end error", (3) layer index; each loop prices one rate step for every member of a group and promotes the whole group if it fits; `-hq`: `min_bpw = rate_floor(base + hq_mult * select_hq_bits)` applied after spending, "so it can push the final average above bpw"; half-integer steps (1.5/2.5/3.5) only below 4 bpw and only with mul1; recipes must cover every budgeted tensor and every entry must match ≥1 tensor; tensors at 16 bpw are excluded from the reported average. — [allocation.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/allocation.py)
- `-hq`: "Increase bitrate of select layers for supported models (MoE mostly) … -hq 2 doubles the promotion"; convert.md: with `-hq` final size may be higher, "For MoE models … about 0.05–0.10 bpw". — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py); [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md)
- Head/embed/MTP/vision bits: `--head_bits` "1-8, 1.5/2.5/3.5 (mul1 codebook), or 16 … default: 6"; `--mtp_bits` default 4; `--vision_bits` "6 for validated towers, else 16"; `--embed_bits` default 16 — "Each embedding is split into 256-wide groups that are rotated and trellis-coded without calibration"; quantized tables are "decoded on the GPU at inference and can be held in system RAM or streamed from disk" (`EXL3_EMBED_STREAM`); existing models via `util/recompile.py --embed_bits`. — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py); [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md)
- Calibration size options are listed under "debug options" (`-cr` 250, `-cc` 2048); trace rows "are not sliced from a concatenated stream" and start at position 0; rows longer than `cal_cols` are truncated. — [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md); [sc_trace.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/sc_trace.py)
- Resume: `-r` "Resume interrupted job from working directory" (explicit, "reversing the behavior from ExLlamaV2"); checkpoint interval 120 s; overridable on resume: in_dir, out_dir, shard_size, mtp_bits, vision_bits, checkpoint_interval, devices, device_ratios, codebook; **not** overridable: bits, recipe, head_bits, hq, ngram_bits, cal_data, cal_rows, cal_cols, hessians; "the resumed job's saved value stands (e.g. --hq stays on when resuming without it)"; some architectures warn "resuming an interrupted quant is not possible". — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py)
- Devices/VRAM: `-d 0,1,2` and `-dr` ratios; parallel mode default, small layers fall back to tile splitting (~1M weights per device minimum); Hessian capture split into passes that fit "beside the loaded weights on every device"; `headroom_min = 1536 MB`, `headroom_frac = 0.06`; extra GPUs help "if PCIe bandwidth is sufficient" and "does not affect memory usage on the first GPU". — [convert_model.py](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/exllamav3/conversion/convert_model.py); [doc/convert.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/convert.md)
- Run time: README "a couple of minutes for smaller models, up to a few hours for larger ones (70B+) on a single high-end consumer GPU"; optimize.md: 27B full pipeline ≈2 h, mostly conversion; sc_measure ≈35 min. — [README](https://github.com/turboderp-org/exllamav3); [doc/optimize.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/optimize.md)
- Memory pitfalls (users, Oct 2026): converter RSS +3.7 GB/layer on glibc (fix `MALLOC_MMAP_THRESHOLD_`) on an R9700 — [issue #460](https://github.com/turboderp-org/exllamav3/issues/460); open PR #562 "Reduces memory use during quantization" (24 Oct) — [issues list](https://github.com/turboderp-org/exllamav3/issues?q=Qwen3.8+OR+GDN+OR+DeltaNet+OR+Qwen3-Next+OR+Qwen3.5)
- Codebook pitfall on ROCm: `test_encode_ideal` fails for mcg/3inst on gfx1201 while mul1 passes (user) — [issue #460](https://github.com/turboderp-org/exllamav3/issues/460); the fork notes conversion kernels "compile but are untested on ROCm" — [exllamav3-rocm](https://github.com/phoenixhaxor/exllamav3-rocm); upstream PR #519 made the K=2 tile quantizer fit 64 KB LDS (author/contributor) — [issues list](https://github.com/turboderp-org/exllamav3/issues?q=ROCm+OR+HIP+OR+AMD+OR+gfx)
- Domain mismatch: "Wikitext-measured recipes transfer poorly, so the trace should be used for measurement" (author) — [doc/optimize.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/doc/optimize.md); third-party wikitext KLD shows SC quants scoring worse than plain ones (see B1) — [jedi95](https://github.com/jedi95/qwen3.8-27b-kld)
- Small-sample KLD caveat (user): KLD figures from "only 10 rows of 2048 tokens of wikitext-2" may not be comparable across quants — [HF discussion GLM-4.7-EXL3](https://huggingface.co/mratsim/GLM-4.7-EXL3/discussions/8)
- Vendored FLA: Qwen3-Next/3.5/3.8 GDN prefill uses vendored Flash Linear Attention Triton kernels; on Windows `triton-windows` is required. — [README](https://github.com/turboderp-org/exllamav3)

### Inferences
- For a 4.0–4.5 bpw target on a 27B dense model with 64 layers, the ends-first default will spend the fractional budget on the first/last layers' highest-priority modules; with mul1 the useful set of rates is {3, 3.5, 4, 5, 6}, so a 4.25 bpw mean can be hit by mixing K4 and K5 (or K3.5/K4/K5) tensors — the optimizer's `--k_step 0.5` only helps below 4 bpw.
- A 27B conversion on a 32 GB R9700 is feasible in principle (per-layer processing; a Qwen3.5-MoE 35B converted on one R9700 per #460) but the glibc RSS growth and the untested-on-ROCm status of the quantizer kernels (mcg/3inst mismatch) argue for converting on an NVIDIA box and only serving on AMD.

### Gaps
- No documented experiment on calibration row length (2048) versus very long-context quality for EXL3; the only related signal is that trace rows are whole conversations from position 0 (so RoPE positions >2048 are never seen in calibration).
- No official VRAM figure for converting a 27B model; only the 1.5 GB/6% headroom rule and the "few hours for 70B+" statement.

## B4. EXL3 on Qwen3-Next / Qwen3.5 / Qwen3.8 hybrid Gated-DeltaNet models: quality at 4 bpw, promoted layers, GDN and 248K-vocab head issues

### Takeaway
Qwen3-Next, Qwen3.5 (dense + MoE), and Qwen3.8-Flash-Next are supported architectures; Qwen3.8-27B is served as `qwen3_5` (64 layers, 16 with KV cache, i.e. 48 GDN layers), has official turboderp quants from 3.0 to 6.0 bpw including SC variants, and runs on gfx1100/gfx1201 with DFlash2 drafting. Public KLD data at 4.00 bpw: 0.0159 (plain) / 0.0214 (SC_H5) on wikitext (third party), "excess KLD" 0.0046 (third party, different metric). The converter ties GDN `in_proj_qkv+in_proj_z` and groups GDN qkv/z in sensitivity measurement; small GDN projections (`in_proj_a/b/ba`) are left unquantized by EXL3, and users report the lm_head is not the sensitive tensor at K6. Known hybrid-specific bugs in Oct 2026 concern recurrent-state slots, the GDN scan, and a ROCm hipBLASLt bug corrupting the fp32 `lm_head` GEMM (fixed by chunking).

### Inferences
- The default ends-first allocation does not know about GDN vs attention; the self-calibration pipeline (shaped noise, tie `in_proj_qkv+in_proj_z`) is the only built-in way to let the 48 GDN layers compete for bits with the 16 attention layers. The user reports (attention promotion helped a lot at K4→K5→K6; GDN in_proj_a/b/ba must stay fp16; head insensitive at K6) suggest a 4.0–4.5 bpw recipe should keep attention q/k/v/o and GDN `in_proj_qkv/z` above the MLP, and that `head_bits` 5 (as in turboderp's SC_H5) is an acceptable place to save ~250 MB on the 248K×5120 head (≈1.27 G weights; 1 bit ≈ 159 MB).
- Nothing indicates the linear-attention layers break the EXL3 format itself; the issues are runtime (recurrent state handling) and ROCm numerical (hipBLASLt) rather than quantisation-time.
